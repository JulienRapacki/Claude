# Lab 2.2 — Set up posting groups

| | |
|---|---|
| Objectif | Set up posting groups (general posting setup, business and product posting groups, specific posting groups) |
| Domaine | Configure financials — 25-30 % |
| Durée | 75 minutes |
| On-prem | Praticable intégralement |

> [!objectif] Ce que tu sauras faire à la fin
> - Distinguer ce que gouverne `General Posting Setup` de ce que gouvernent les `specific posting groups`.
> - Compléter une combinaison `Gen. Bus. Posting Group` / `Gen. Prod. Posting Group` et prévoir quel compte sera mouvementé avant de poster.
> - Diagnostiquer un blocage de validation causé par une combinaison de posting groups incomplète.
> - Retrouver, sur une écriture postée, quel posting group a déterminé quel compte.
> - Différencier un compte de résultat (`General Posting Setup`) d'un compte de bilan (`Customer Posting Group`, `Inventory Posting Setup`).

## 1. Praticabilité on-prem

**Oui.** L'intégralité du paramétrage des posting groups est en base ; aucune dépendance Cloud.

## 2. Pré-requis

> [!attention] Écritures définitives et paramétrage non réversible sur les master data
> Ce lab poste une facture de vente : les `G/L Entries` produites sont définitives et non supprimables. Il modifie aussi les posting groups d'un client et d'un article existants — un changement qui n'affecte pas les écritures déjà postées, mais qui s'applique à tout document futur tant que tu ne l'as pas rétabli. **Jamais sur la production.** Prends une sauvegarde ou travaille sur une copie de base de test avant de commencer.

- [ ] Société `CRONUS` ou copie de base de test, restaurable.
- [ ] Un `customer` et un `item` utilisables pour un test de facturation, sans historique bloquant.
- [ ] Un `G/L Account` de résultat disponible pour recevoir un test de compte de vente (ou la possibilité d'en créer un dédié).
- [ ] Permissions sur les pages `General Posting Setup`, `General Business Posting Groups`, `General Product Posting Groups`, `Customer Posting Groups`, `Inventory Posting Setup`, `Sales Invoices`.

Les codes et montants ci-dessous sont **arbitraires**, choisis pour ne rien percuter dans `CRONUS`. Adapte-les en cas de conflit.

## 3. Mission

Tu prépares une combinaison de posting groups dédiée, pour observer sans ambiguïté quel compte est mouvementé et par quel paramétrage.

### 3.1 Repérer les posting groups actuels du customer et de l'item test

{nav: Sales > Customers > (ouvrir le client) > Invoicing FastTab ?}

- Note la valeur actuelle de `Gen. Bus. Posting Group` et de `Customer Posting Group`. Tu devras les restaurer en fin de lab.

{nav: Tell Me (Alt+Q) > Items > (ouvrir l'article) > Invoicing FastTab ?}

- Note la valeur actuelle de `Gen. Prod. Posting Group` et de `Inventory Posting Group`.

### 3.2 Créer une combinaison dédiée de business/product posting groups

{nav: Tell Me (Alt+Q) > General Business Posting Groups > New}

- Dans `Code`, saisis un code arbitraire, par exemple `LABBUS`.

{nav: Tell Me (Alt+Q) > General Product Posting Groups > New}

- Dans `Code`, saisis un code arbitraire, par exemple `LABPROD`.

### 3.3 Compléter General Posting Setup pour cette combinaison

{nav: Tell Me (Alt+Q) > General Posting Setup > New}

- Dans `Gen. Bus. Posting Group`, sélectionne `LABBUS`.
- Dans `Gen. Prod. Posting Group`, sélectionne `LABPROD`.
- Avant de remplir toute la ligne : détermine par toi-même quel(s) compte(s) sont réellement nécessaires pour poster une simple facture de vente d'article, et lesquels tu peux volontairement laisser vides pour l'instant. Ne remplis que ce dont tu as besoin.
- Renseigne `Sales Account` avec un `G/L Account` dédié au test, choisi ou créé pour être facilement identifiable.

### 3.4 Appliquer les nouveaux posting groups au customer et à l'item

{nav: Sales > Customers > (ouvrir le client) > Invoicing FastTab ?}

- Dans `Gen. Bus. Posting Group`, sélectionne `LABBUS`.

{nav: Tell Me (Alt+Q) > Items > (ouvrir l'article) > Invoicing FastTab ?}

- Dans `Gen. Prod. Posting Group`, sélectionne `LABPROD`.

### 3.5 Prédire, puis vérifier le compte mouvementé

{nav: Sales > Sales Invoices > New}

- Crée une facture pour le client de l'étape précédente, avec une ligne sur l'article de l'étape précédente, quantité et prix arbitraires.
- Avant de poster : d'après ce que tu as renseigné en 3.3, détermine toi-même quel `G/L Account` doit recevoir le montant de la ligne de vente. N'ouvre pas encore les écritures pour vérifier, formule ta prévision.
- Valide (`Post`) la facture.
- Ouvre les `G/L Entries` produites et confronte le compte réellement mouvementé à ta prévision.

### 3.6 Provoquer et diagnostiquer une combinaison manquante

{nav: Tell Me (Alt+Q) > Items > (ouvrir un second article, avec un Gen. Prod. Posting Group différent) > Invoicing FastTab ?}

- Choisis ou crée un article dont le `Gen. Prod. Posting Group` n'a **aucune** ligne correspondante avec `LABBUS` dans `General Posting Setup`.

{nav: Sales > Sales Invoices > New}

- Crée une facture pour le même client (`Gen. Bus. Posting Group` = `LABBUS`) avec une ligne sur cet article.
- Valide (`Post`). Ne suppose pas le résultat : lis le message exact et note-le.
- Reviens sur `General Posting Setup` et complète la combinaison manquante pour lever le blocage, puis reposte.

### 3.7 Comparer avec un compte de bilan porté par un specific posting group

{nav: Tell Me (Alt+Q) > Customer Posting Groups > (ouvrir le Customer Posting Group du client test)}

- Repère la valeur de `Receivables Account`.
- Détermine, sans le supposer, si ce compte dépend du `Gen. Bus. Posting Group` que tu as changé à l'étape 3.4, ou d'un paramétrage totalement indépendant. Vérifie ta conclusion sur ta base.

### 3.8 Relier chaque écriture postée à son posting group déclencheur

{nav: Sales > Posted Sales Invoices > (ouvrir la facture postée de l'étape 3.5) > Navigate ?}

- Ouvre l'ensemble des écritures produites par cette facture.
- Pour chaque compte général mouvementé, détermine s'il provient de `General Posting Setup` (croisement business/product) ou d'un `specific posting group` (customer, inventory…). Ne le déduis pas de mémoire : croise avec les pages consultées aux étapes précédentes.

> [!astuce] Chemins de navigation
> Passe par `Tell Me` (`Alt+Q`) avec le nom anglais de la page quand l'arborescence de menu te manque. Un chemin marqué `?` est à confirmer sur ta base : les onglets d'une fiche varient selon la personnalisation et la version.

## 4. Points de contrôle

- [ ] `LABBUS` et `LABPROD` existent respectivement dans `General Business Posting Groups` et `General Product Posting Groups`.
- [ ] Une ligne `General Posting Setup` existe pour le couple `LABBUS` / `LABPROD`, avec `Sales Account` renseigné et le reste volontairement laissé vide ou complété selon ton diagnostic de l'étape 3.3.
- [ ] Le client test porte `Gen. Bus. Posting Group` = `LABBUS` ; l'item test porte `Gen. Prod. Posting Group` = `LABPROD`.
- [ ] La facture de l'étape 3.5 est postée, et le `G/L Account` réellement mouvementé correspond (ou non, note lequel) à ta prévision.
- [ ] L'échec de l'étape 3.6 est reproduit, avec le message exact noté, et **aucune** `G/L Entry` correspondante créée avant correction.
- [ ] Après complément de la combinaison, la seconde facture se poste sans erreur.
- [ ] Le `Receivables Account` du `Customer Posting Group` est identifié, et sa dépendance (ou non) au `Gen. Bus. Posting Group` est vérifiée sur ta base, pas supposée.
- [ ] Via `Navigate` sur la facture postée, chaque compte général est attribué à sa source : `General Posting Setup` ou `specific posting group`.

## 5. Pièges d'examen

> [!piege] General Posting Setup ne couvre pas tous les comptes
> Il détermine les comptes de résultat (vente, achat, coût des ventes) selon le croisement business/product. Les comptes de bilan (créances, dettes, stock) viennent d'ailleurs.

> [!piege] Qui porte quel posting group
> `Gen. Bus. Posting Group` se pose sur le tiers (customer, vendor) ; `Gen. Prod. Posting Group` se pose sur ce qui est vendu ou acheté (item, G/L account, resource). Les confondre est une erreur fréquente à l'examen.

> [!piege] Customer Posting Group est indépendant de Gen. Bus. Posting Group
> Deux tables différentes, deux rôles différents. Changer l'un ne change pas mécaniquement l'autre : c'est à vérifier, pas à supposer.

> [!piege] Une combinaison incomplète ne bloque qu'au moment de poster
> Rien n'empêche de saisir la facture avec une combinaison manquante. L'erreur n'apparaît qu'à la validation, jamais avant.

> [!piege] Inventory Posting Setup croise d'autres axes
> Ce n'est pas `Gen. Bus. Posting Group` x `Gen. Prod. Posting Group`, mais `Location Code` x `Inventory Posting Group`. Deux matrices indépendantes, à ne pas mélanger dans une réponse d'examen.

> [!piege] Changer un posting group sur une fiche n'est pas rétroactif
> Les écritures déjà postées gardent le compte qui a servi à leur création. Seuls les documents futurs suivent le nouveau paramétrage.

## 6. Questions de contrôle

1. Which two posting groups, and set up on which master records, combine in `General Posting Setup` to determine the sales revenue account on an invoice line?
2. A customer's `Customer Posting Group` defines its `Receivables Account`. If you change that customer's `Gen. Bus. Posting Group`, does the `Receivables Account` change as well? Why or why not?
3. What happens when Business Central cannot find a `G/L Account` for the combination of posting groups on a document line at posting time?

> [!reponses] Corrigé
> **1.** `Gen. Bus. Posting Group`, posé sur le customer (ou vendor), et `Gen. Prod. Posting Group`, posé sur l'item (ou le G/L account, la resource). Leur croisement dans `General Posting Setup` détermine le `Sales Account`.
>
> **2.** Non. `Receivables Account` vient du `Customer Posting Group`, une table indépendante de `General Posting Setup`. Les deux posting groups n'ont aucun lien mécanique entre eux.
>
> **3.** La validation (`Post`) est refusée avec un message nommant la combinaison ou le type de compte manquant, et aucune écriture n'est créée. Le libellé exact est à confirmer sur ta base.
>
> Toute réponse fausse part dans `mb800/erreurs.csv`, avec sa cause.

## 7. Nettoyage

Réversible en partie seulement.

- Restaure sur le client et l'item testés les valeurs de `Gen. Bus. Posting Group`, `Gen. Prod. Posting Group`, `Customer Posting Group` et `Inventory Posting Group` notées à l'étape 3.1.
- Supprime la ligne `General Posting Setup` du couple `LABBUS` / `LABPROD` si elle n'est plus référencée par aucune écriture.
- Supprime `LABBUS` et `LABPROD` dans `General Business Posting Groups` et `General Product Posting Groups` si BC l'autorise ; sinon, laisse-les inutilisés.
- Les `G/L Entries` créées par les factures postées sont définitives. Si ta base doit rester propre, restaure la sauvegarde prise en pré-requis.
