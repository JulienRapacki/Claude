# Lab 1.4 — Set up dimensions

| | |
|---|---|
| **Objectif** | Set up dimensions (dimensions, dimension values, default dimensions, dimension combinations) |
| **Domaine** | Set up Business Central — 20-25 % |
| **Durée estimée** | 90 minutes |

## Praticabilité on-prem

**oui** — l'intégralité du paramétrage des dimensions est en base, aucune dépendance Cloud.

## Pré-requis

- Société **CRONUS** ou copie de base de test. **Jamais la production** : ce lab crée des écritures comptables.
- Point de restauration ou sauvegarde avant de commencer : les G/L Entries produites ne sont pas supprimables.
- Un customer et un vendor utilisables, un G/L Account de charge autorisant la saisie directe.
- Permissions suffisantes pour la page *General Journal* et pour la table *Dimension*.

Codes et montants ci-dessous : **arbitraires**, choisis pour ne rien percuter dans CRONUS. Adapte-les si tu as un conflit.

## Mission

Tu prépares une société à un suivi analytique par projet et par canal de vente.

1. Crée deux dimensions : `PROJECT` et `CHANNEL`. Donne à chacune trois *dimension values*, dont une avec **Dimension Value Type** autre que `Standard` et une passée en **Blocked**.
2. Détermine lesquelles des deux méritent d'être des **global dimensions** plutôt que de simples **shortcut dimensions**, et applique ton choix. Avant de lancer quoi que ce soit : identifie ce que l'opération de changement de global dimension fait réellement aux écritures existantes, et pourquoi elle ne se lance pas à la légère sur une base vivante.
3. Sur un customer, pose une **default dimension** `PROJECT` avec **Value Posting** = `Code Mandatory`. Sur un G/L Account, pose une default dimension `CHANNEL` avec **Value Posting** = `Same Code` sur une valeur précise.
4. Saisis et valide une ligne de *General Journal* qui **doit échouer** à cause du `Code Mandatory`, puis corrige-la et valide.
5. Provoque un conflit : une même écriture recevant deux valeurs `CHANNEL` par défaut venant de deux sources différentes. Résous-le par **Default Dimension Priorities**, sans toucher aux default dimensions elles-mêmes.
6. Bloque une combinaison `PROJECT` + `CHANNEL` via **Dimension Combinations** (teste `Blocked` puis `Limited`), et vérifie le comportement à la validation.
7. Consulte le résultat dans **Analysis by Dimensions** et détermine ce qu'il faut faire pour que les dernières écritures y apparaissent.

Chemins : passe par **Tell Me** (`Alt+Q`) avec le nom anglais de la page — les arborescences de menu varient selon le role center et la version.

## Points de contrôle

- Les *dimension values* bloquées et les types non `Standard` ne sont pas sélectionnables en saisie ; note le message exact.
- L'écriture de l'étape 4 est refusée avec un message nommant la dimension manquante, et **aucune** G/L Entry n'est créée. Vérifie-le, ne le suppose pas.
- Après validation réussie, les G/L Entries portent un **Dimension Set ID** non nul, et les deux dimensions sont visibles dans les *dimension set entries* de cette écriture.
- Le conflit de l'étape 5 se résout par la priorité la plus basse gagnante — vérifie le sens effectif sur ta base avant de conclure.
- La combinaison `Blocked` refuse la validation ; la combinaison `Limited` n'interdit que certains couples de valeurs. Les deux messages diffèrent : relève-les.
- **Analysis by Dimensions** n'affiche rien de neuf tant que l'analysis view n'a pas été mise à jour. C'est un piège de production autant que d'examen.

## Pièges d'examen

- **Global** vs **shortcut** vs **budget** dimensions : combien de chaque, lesquelles sont filtrables directement sur les entries, lesquelles ne le sont pas.
- Changer une global dimension n'est pas un paramétrage mais un traitement, avec un impact sur les écritures existantes. Savoir *quand* c'est encore possible vaut plus que savoir où cliquer.
- **Value Posting** : `Code Mandatory`, `Same Code`, `No Code` — et surtout, ce qui se passe quand deux default dimensions se contredisent sur une même écriture.
- Une default dimension posée sur un compte ne se comporte pas comme une default dimension posée sur un customer ou un vendor : la priorité tranche, pas l'ordre de saisie.
- **Dimension Combinations** `Blocked` et `Limited` ne bloquent pas au même niveau : l'un interdit le couple de dimensions, l'autre des couples de valeurs.
- Les dimension set entries sont partagées et non modifiables : on ne corrige pas les dimensions d'une écriture validée, on extourne.

## Questions de contrôle

1. How many global dimensions and how many shortcut dimensions can a Business Central company have, and which of them can be used directly as a filter on G/L Entries?
2. A default dimension on the customer says `Code Mandatory` for `PROJECT`; a default dimension on the G/L account says `No Code` for the same dimension. A sales invoice hits both. What decides the outcome, and where do you change it?
3. What is the difference in posting behaviour between a `Blocked` and a `Limited` dimension combination?

<details>
<summary>Réponses</summary>

1. 2 global, 8 shortcut (les 2 premières shortcut étant les globales). Seules les globales sont des champs sur les entries et donc filtrables directement ; les autres passent par le dimension set.
2. Le conflit se tranche par **Default Dimension Priorities**, paramétrées par *source code* et par table. Vérifie sur ta base le sens de la priorité avant de répondre en situation.
3. `Blocked` interdit toute écriture combinant les deux dimensions ; `Limited` autorise la combinaison mais interdit certains couples de **valeurs**, définis dans la matrice.
</details>

## Nettoyage

Partiellement réversible. Les *dimension values* non utilisées se suppriment ; **dès qu'une valeur a servi à une écriture validée, elle ne se supprime plus** — on la passe en `Blocked`. Les G/L Entries créées par le lab sont définitives : si ta base doit rester propre, restaure la sauvegarde prise en pré-requis. Si tu as modifié une global dimension, la restauration est le seul retour arrière raisonnable.
